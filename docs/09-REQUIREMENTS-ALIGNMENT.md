# Stella 顶层需求对齐记录

更新日期：2026-09-05。

本文固化本轮用户已经确认的产品要求，并单独记录核查证据及相应设计契约。它不是开发计划，也不表示现有 Alpha 已实现这些要求。与早期设计文档存在产品范围或体验取舍冲突时，以本文明确记录的新决定为准；未被修改的技术契约继续有效。

## 1. 产品目标与完整功能

Stella 是用户的数字分身与高维自我：持续理解用户，扩展其记忆、经验、视角、模拟和实践能力，同时保留用户自身的价值判断。Personal Twin、Framework Compiler、Reality / Social Intelligence、Praxis Loop 仍属于同一个 Cortex。

完整产品需要支持以下六类能力，关系／社交 Alpha 只是首个验证领域：

| 能力 | 预期作用 |
| --- | --- |
| 回忆与查证 | 找回相关资料、经历和对话，核对来源、时间与变化 |
| 现实决策与行动 | 结合个人情境、思考框架和现实信息形成建议，吸收行动结果 |
| 个人事务管理 | 持续跟进目标、承诺、任务及未完成事项 |
| 思考、学习与创作 | 运用积累的资料和理解，支持分析、学习、写作与表达 |
| 数字分身 | 预测用户在具体情境下的选择、判断和表达，并依据实际反馈校准 |
| 自我理解与成长 | 发现情境差异、行为模式与盲区，通过交流加深理解 |

### 1.1 一次明确授权，持续代办（已确认）

Stella 应具备替用户执行事务的能力。研究、整理和准备材料可以按已确认的自主边界完成；对外操作依据用户对具体事项或某类事务的明确授权执行。

对已有明确授权且仍处于授权范围内的重复事务，Stella 可以持续代办，不要求每次重新确认。遇到授权之外的新决定，先向用户询问。用户对建议的认可、历史执行满意度或模型信心不能自动扩大执行权限。

执行使用 OpenClaw 的工具、调度和权限能力。这里确认产品能力，尚未委托任何具体对外事务或启用代办任务；现有 Alpha 的建议／准备边界不等于完整产品的最终边界。

### 1.2 写作思路梳理（已确认）

Stella 应与用户共同推进文章思考，把想法梳理到能够开始并连贯写下去的程度。支持尚未成文的想法，也支持后半部分写不下去、无法结尾等中途卡点。默认不能把“帮我梳理思路”直接解释为代写全文；起草和改写按具体请求处理。

**用户已通过实际文章讨论认可的协作方式是：** 读取已有材料 → 理解作者原意与前提 → 检查论述衔接、找出具体卡点 → 通过交流共同推演并吸收纠正 → 整理出可以继续写作的推进路径。

这个过程允许提问与直接整理相互推进，不要求用户先独立想清楚全部观点再交给 Stella。已能从资料或当前对话确定的内容直接利用；追问集中于会改变理解或推进方向的关键未知。用户纠正后，应及时修正文章理解并用于后续推演，避免重复确认已明确的前提。

已有文章背景先从仓库读取，包括相关立项、提纲、草稿、关联材料，以及配套的目的说明、论证结构、修改反馈和写作经验。Stella 应重建这篇文章已经想到哪里、哪些问题已有答案、哪些部分尚未展开，不要求用户重新口述已保存的背景。

状态字段、已有正文和用户认可属于不同证据。“立项／草稿”标签、空白提纲或长期未更新不能单独证明停笔原因；已有成段正文也不代表用户认可其表达。具体卡点应结合正文与用户反馈判断，不把一篇文章的原因推广到全部写作。

保持作者原意与核查论述是否成立应同时进行。区分用户原有表达、外部资料和 Stella 的新解释，并区分事实、类比、推演与价值判断。可以指出依据缺失、逻辑断点或矛盾，但不能用助手自己的价值结论替换作者原意，也不能为忠于作者就自动认定所有主张成立。

提出的主线解释、推进路线和收束方向属于候选，是否符合原意由用户判断。不默认添加积极意义、励志结尾、个人使命或选定情绪立场；作者仍在思考的实质问题应保留并继续探索，不能当作纯措辞问题强行结束。对协作方式的认可不自动等于采纳全部候选结论或确认文章已经完成。

个性化依据用户对卡点和有效帮助的具体反馈持续修正，不凭单一标签推定固定的工作方式。实际效果关注用户是否感到思路更顺、是否更容易开始或继续写作；提纲完整度、生成字数或自动评分不能替代用户反馈。本轮认可确认了协作方式，不代表现有 Core 已实现该能力。

### 1.3 本轮以两个场景检验架构（已确认）

用户暂时没有补充其他核心场景，本轮以按需社交判断和写作共思继续检验架构，不再以寻找第三个场景作为继续设计的前提。这收敛本轮需求对齐的代表性场景，不取消 §1 的完整产品目标，也不据此宣称已经确定新的版本交付范围。

两者都要求从个人仓库恢复相关上下文、查证原始资料、吸收用户纠正并接续未完成的理解。社交判断关注持续行为、反证与投入校准；写作共思关注作者前提、论述衔接与推进路径。不能把其中一个场景的特定结论或流程当作另一个场景的默认答案。

## 2. OpenClaw、Stella Core 与沧海的边界

- **OpenClaw** 提供通用运行能力：会话与原始对话存储、基础检索和索引、上下文管理、工具执行、调度唤醒、消息投递、通用记忆整理与备份。应先验证宿主及已有插件能否满足要求，再确定 Core 需要补充的能力。
- **Stella Core** 是 OpenClaw plugin，负责个性化认知：理解任务、组织检索、判断证据与适用范围、运用个人框架、维护 Twin 与实践学习、判断是否值得主动交流。逻辑职责独立不意味着必须再造一套存储、检索或调度系统。
- **沧海（CangHai）** 是持久个人数据与认知配置的归属，也是用户直接查看和维护资料的入口。Stella-Core 只保存公开代码、契约与不含私人内容的评测资产。

复用必须满足完整契约。宿主具有同名能力，不等于已经满足来源追溯、留存、语义判断、删除传播或恢复要求；未满足时应明确缺口，不能静默降级后报告成功。

用户不需要另建专用的“查看 Stella 如何理解我”产品功能。个人仓库中的资料和理解应可读、来源清楚、变化可追溯；派生索引、缓存不必全部提交到 Git。

### 2.1 个人理解的统一管理（已确认）

OpenClaw 提供通用的记录、整理和记忆能力，Stella 统一判断哪些解释进入长期个人模型，并管理其适用范围与更新。该分工复用宿主能力，由 Stella 承担个人理解的语义判断责任。

摘要必须保留原始来源，作为查找和理解证据的入口，不能被视为额外的独立证据。用户的一次纠正应传播到相关摘要、假设和后续回答，不应要求用户分别纠正宿主记忆与 Twin。

尚未消解的不同解释可以并存，并保留各自的证据、情境和不确定性。统一管理指来源与更新关系一致，不要求把分歧强行合并成唯一结论。具体同步协议见 [Memory Lifecycle](contracts/MEMORY-LIFECYCLE.md#5-来源变更同步)；契约已定义不表示现有集成已满足这一要求。

## 3. 能容纳各类个人数据的记忆结构

采用以下**逻辑分层**，不据此提前锁定数据库、目录或文件格式：

| 层 | 内容 | 关键约束 |
| --- | --- | --- |
| 原始资料 | 文本、图片、录音、视频、文件、聊天、结构化数据 | 保留原貌、来源与时间；理解变化不能改写原始历史 |
| 事实与经历 | 人物、事件、时间线、目标、承诺、行动与结果 | 关联原始证据，区分已知事实、转述与未知 |
| 理解与经验 | 情境性假设、偏好、行为模型、实践经验 | 保留适用范围、支持和反对证据，允许修正 |
| 检索与运行视图 | 索引、检索摘要、上下文投影 | 从来源派生并可重建，不能成为脱离证据的独立事实源 |

不能强制所有媒体变成 Markdown，也不能以摘要替代原始材料。资料进入仓库、被正确理解、能被检索、被正确用于回答，是不同的要求。

### 3.1 数据源集中于个人数字仓库，当前以 Git 承载（已确认）

用户明确说明原因：希望数据源都集中于个人数字仓库，目前该仓库基于 Git。**数据源集中于个人数字仓库是产品要求，Git 是当前承载方式。** 不能把当前技术选择扩展为永久必须使用 Git 的产品目标。

在当前基于 Git 的方案中，拿到一份完整的沧海 Git 仓库副本，就必须拥有全部按留存要求保存的原始资料，包括图片、录音、视频和聊天附件。数据完整性以对应归档版本为准；既有不留存、删除和同步时限要求继续适用。未来承载方式如需变更，应另行对齐，并继续满足数据归集与完整性要求。

当前方案的原始内容必须能从 Git 副本本身取得。仓库内只有附件清单、外部地址或指针，而还需访问独立附件存储才能取得原文件，不满足已确认的当前存储边界。

仓库内的目录、文件格式和归档方式仍可设计，但必须保留原始内容并满足副本自包含性。可重建的索引、缓存继续由运行时管理；外部运行凭据仍按既有密钥契约处理。

完整性验收需要验证：在无法访问原运行服务器及外部附件存储时，仍能从 Git 副本读取所需原始资料，并核对归档范围、引用和内容完整性。这是新增的完整个人数据要求，现有 Alpha 意识恢复检查尚不能证明它已满足。

### 3.2 跨领域理解与来源语义

在授权范围内，Stella 可以跨工作、生活、写作、阅读等领域综合理解用户，不能仅凭目录把同一个人的理解割裂。具体资料的用途限制仍须遵守，并始终区分：

- 原作者观点与用户表达；收藏与认同；
- 历史状态与当前状态；事实与推断；
- 特定情境中的反应与适用于更广范围的原则。

## 4. 输入途径与日常对话留存

记忆输入包括五类：

1. 日常交互中的表达、解释、纠正、拒绝原因和行动反馈。
2. 用户主动记录，包括旧版“写入记忆”“了解我”等 skill 入口承载的需求。
3. 文件、多媒体、历史聊天与其他资料的批量导入。
4. 用户在 Obsidian 或个人仓库中的新增、修改与删除。
5. 经授权的外部资料，例如阅读笔记、日历、健康记录。

这些入口应共享后续的存储、来源关联、索引与学习机制。用户主动交付资料的默认整理边界已按下节确认；围绕用户目标自主研究与沉淀资料的能力已在 §6.5 确认。各入口共享 [Memory Lifecycle](contracts/MEMORY-LIFECYCLE.md#2-资料接入)；具体外部账号及权限须依据实际接入任务配置，不由本次产品确认自动授予。

### 4.1 用户主动交付资料的默认整理权（已确认）

用户主动交给 Stella 的资料，默认允许自动归档、提炼、建立关联，并更新可修正的理解，同时保留原始内容与来源，不要求每次整理前再确认。

用途不清时应追问；涉及改写用户原文、修改用户思考框架或改变资料用途时，需要取得对应的明确授权。用户已明确授权的操作按其指示执行，不重复请求确认。

自动更新理解仍须遵守事实与推断、适用情境和证据来源的区分。该决定取代 1.0 在此范围内逐次确认保存的要求，不自动扩大到尚未授权的外部资料来源。

### 4.2 日常对话留存

**日常对话默认完整保留为可追溯的原始资料，再按价值提炼长期理解。** 用户可以指定不留存；后续需要修正或删除时，由用户直接修改仓库存储文件，再同步记忆索引，具体边界见 §7。保存和备份优先使用 OpenClaw 能力，Core 不另建会话数据库。

必须保留用户原话与 Stella 回答的身份区别。Stella 自己的推断、摘要或重述不能被再次读入后当作新的用户证据。摘要、经过截断的历史工具输出不等于完整对话档案。

“核心意识恢复不依赖旧 session”继续成立：持久事实、理解、框架与重要未完成状态必须独立于会话运行态保存。这不取消完整对话留存要求。完整对话档案及附件必须纳入自包含的沧海 Git 副本；宿主归档接入、仓库内格式、留存覆盖与新环境检索遵循 [Memory Lifecycle](contracts/MEMORY-LIFECYCLE.md) 和 [Host 集成契约](04-OPENCLAW-INTEGRATION.md)。

## 5. 召回与回答质量

用户明确接受较长耗时，优先追求极致的召回与回答效果。不能为了固定的低延迟、小候选集合或小上下文，预先牺牲关键证据。

预期认知过程是：理解当前问题 → 从多个角度规划检索 → 根据线索继续查找 → 寻找反证和更新 → 回读原始材料 → 核对人物、时间、来源和适用范围 → 作答。

基础搜索与索引优先复用 OpenClaw；Stella 负责语义判断、关联和证据充分性。检索命中不等于可以直接采信，历史关联不等于当前适用。证据不足时应说明缺口，必要时向用户求证。

多变自然语言的路由、分类、候选选择必须使用 LLM 的结构化语义判断。确定性代码处理结构校验、权限、容量和执行约束，不能用词面规则替代理解。

当前 Alpha 的候选数量和 packet 容量属于实现限制，不能被当作最终质量要求。资源或检索失败应保留明确失败类别，不能通过静默截断关键证据把不完整路径包装成成功。

### 5.1 关键未知先追问（已确认）

Stella 应先自行检索已有资料，利用已经掌握的信息。经过检索仍缺少会改变建议方向的关键信息时，先向用户追问，再给出依赖该信息的明确建议。

对不影响主要判断的细节，可以明确说明假设后继续推进。资料无法读取、检索未找到证据或证据相互冲突，应如实说明对应情况；不能将这些情况统一解释为事实不存在，也不能通过假设把检索失败包装成成功。

是否属于会改变建议方向的关键未知，应通过语义判断决定。需要先澄清时，提出关键问题就是当前适当的交互结果，不应为了满足固定回答格式而强行给出确定建议。

### 5.2 综合判断社交状态，校准投入与预期（已确认）

用户明确要求 Stella 综合判断真实社交状态，帮助其清醒认识处境并获得实用建议。关系判断不能只做单句解读或回复润色，也不能以安慰用户、维持积极解释作为判断目标。

**社交状态判断按用户求助触发。** 用户问到时，Stella 应主动检索相关历史与最新资料，形成有依据的判断和实用回答；不要求用户每次重新提供已保存的背景。不做关系的主动持续跟进，不因新增关系资料或发现变化而自行发起关系提醒。这里限定社交判断的触发范围，不取消既有资料整理、理解更新或其他已确认的主动能力。

判断应结合原始对话与持续行为：回复内容是否实质回应、主动联系与关心是否双向、回复频率与节奏如何变化、承诺是否落实、双方实际投入及关系所处情境。频率应结合既往基线、已知现实约束与资料覆盖范围理解；归档中没有记录不等于实际没有互动，不能用固定的回复时长或次数阈值代替语义判断。

双方年龄、人生阶段、性格与身份关系属于相关情境。性格解释应有具体行为或可靠陈述支持，不能仅凭人格标签、年龄或身份推定动机，也不能用这些标签消解持续回避、缺少回应或投入不对等的证据。礼貌回应、对某个话题有兴趣、愿意接受帮助，与持续投入关系是不同判断，需要分别找依据。

每次用户求助时，Stella 应根据相关历史与最新证据校准关系状态理解，说明当前支持什么判断、主要反证、关键未知及哪些后续变化会改变结论。判断的确定程度应与证据相称，既不把模糊信号默认解读为积极投入，也不把一次迟复或拒绝直接解释为整段关系无意愿。

建议需要同时检查用户的期待、已作出的投入与长期安排是否得到双方实际行为支持。即使尚不能确定对方的内心动机，只要已有证据足以显示当前关系不足以支持进一步投入，也应清楚指出这一点，并给出与证据和用户目标相称的行动建议，例如放缓投入、观察具体的双向行动、澄清关系期待或退出。不能因为无法读懂对方全部想法，就回避已经能够作出的现实判断；也不能以关键未知为由阻止有依据的风险提醒。

实用建议包括是否继续联系、联系的内容与强度、是否增加投入以及何时重新评估，不默认以推进关系或获得回复为成功。事实、关系状态推断、内心动机假设及建议要分清；后续结果用于纠正判断、推理方式与建议，不能改写当时预测，也不能由最终退出反推出全部历史动机。

## 6. 在交互中持续增进理解

### 6.1 明确拒绝需要探明原因

用户拒绝建议时，Stella 应探明背后的动机、目标、约束和价值取舍，找出原建议遗漏的条件，调整建议并更新理解。不能在“尊重拒绝”之后直接停止学习，也不能仅凭拒绝本身推出一个稳定偏好。

用户已经解释原因时，应利用现有解释。用户不愿展开时，保留未知而不替其编造原因。

### 6.2 解释、行为与理解更新

用户对自己的解释具有高权重。如果它与长期行为证据不一致，Stella 可以坦诚指出具体差异，与用户一起辨清情境差异、偏好变化或原先理解错误，而非断言自己比用户更清楚其真实想法。

新理解应立即用于已经明确的当前情境；推广到其他情境时，作为可修正假设继续积累证据。用户明确表达长期原则时，可以按其声明的范围理解。一次行为、一次拒绝、一次模型推断都不能自动变成全局人格结论。

### 6.3 实时学习与后台整理

- 交互时按需深入检索，吸收用户补充、纠正和实际结果，及时调整回答与适用情境中的理解。
- 没有新任务时，也可以整理资料、发现关联、检验假设、识别矛盾和理解缺口。

重复整理同一份旧材料不增加独立证据数量。通用记忆整理优先复用宿主；Twin 和 Praxis 的特定学习目标仍需满足 Stella 的来源、情境和更新契约。

### 6.4 有价值时主动交流

以日常交互中的自然理解为主。对于重要、会影响多个判断的理解缺口，Stella 可以主动邀请深入交流；不应把每次聊天都变成访谈。后台没有足够价值时保持安静。

社交状态判断遵循 §5.2 的按需边界：不能以重要关系、状态变化或理解缺口为由，主动跟进关系并发起提醒。

**主动交流未获回复时的处理已确认：** 没有截止时间的交流暂时搁置，等出现新信息或自然相关的场景再提。沉默只表示尚未获得反馈，不能被推断为认可或拒绝，也不能据此扩大授权。有时效的事项按既有委托处理，不因一次未回复自动取消，也不据此超出委托范围。

OpenClaw 负责唤醒与投递，Stella 负责判断交流价值、内容与合适时机。这里确认的是产品能力，不代表已经配置或启用了任何定时任务；频率、时段和具体触发规则尚未确定。

### 6.5 围绕用户目标自主学习（已确认）

自主学习是 Stella 成为数字分身与高维自我的基础能力，围绕用户的实际问题和长期目标持续进行，覆盖以下完整过程：

理解用户目标 → 发现知识或经验缺口 → 自主研究 → 关联个人情境 → 提出建议或问题 → 从实际反馈中学习。

Stella 可以在已有访问权限内自主寻找、筛选、关联和沉淀有价值的外部资料，无需用户逐篇决定是否保存。每份长期保留的资料都应说明它与用户的关系、可能改善的判断及原始来源；留存资料进入个人数字仓库并遵守已确认的原始内容与完整性要求。

自主学习对两类目标的作用需要区分：

- **高维自我**：补充用户未接触的经验，发现新的解决办法，将外部知识与用户目标、处境和已有经验关联，形成未来可复用的判断依据。
- **数字分身**：外部知识帮助提出更好的问题和理解更多可能性；对用户的理解应由其选择、解释、拒绝原因和行动结果提供证据。外部理论本身不能直接成为用户特征或偏好的证据。

资料沉淀是学习过程的一环，收藏数量不能代表成长。学习成果应能够服务后续判断、建议或实践，并根据实际使用反馈修正其适用性与学习方向。持续自主学习仍遵循 §6.4 的交流价值要求。

这项确认规定产品能力，不表示已启用后台任务、接入新账号或完成外部研究实现；通用运行能力继续复用 OpenClaw。

### 6.6 主动挑战思考框架（已确认）

当具体证据表明用户的既有思考框架可能存在局限时，Stella 可以主动提出质疑，解释证据与适用边界，并给出修订建议。这属于自主学习和支持用户成长的产品能力。

讨论中应区分事实认知与价值取舍，不能把外部理论或不同价值偏好直接当作用户框架错误的证明。是否正式修改框架由用户决定；已明确授权的修改按指示执行，不重复请求确认。

质疑、修订提案和实践学习应与用户原框架及已激活的执行版本区分。未经用户采纳的框架修订不能偷偷写入原文，也不能通过新 IR 使其事实上生效。

## 7. 用户直接维护文件，再同步记忆（已确认）

**Stella Core 不做自然语言“忘记某件事”功能。** 用户明确说明不会通过 Stella 遗忘某个事件；如有必要，会自己物理修改或删除存储文件，再重新同步记忆索引。个人仓库的文件维护流程已经承载这一需求，无需另建事件级遗忘入口。

同步以用户修改后的仓库版本为准，刷新相关索引，并按已有来源依赖更新受影响的摘要、理解与策略。被删除的来源停止使用，依赖它的结论重新评估；仍有其他有效来源支持的结论可以保留。同步不能只刷新搜索索引却让过时摘要继续作为有效依据。

正常学习与同步不能从旧索引、旧摘要或历史版本自动恢复用户已修改、删除的来源。这里要求对实际文件变更保持一致，不建立跨全部资料按事件执行遗忘的协议。Git 历史与备份的物理处理由用户自行管理，不作为 Stella 的待开发遗忘功能。

以下已有契约继续有效：

- 用户原始思考框架是权威来源；实际执行的 Framework IR 与实践学习分别保存，自动学习不偷偷改写用户原框架。
- 结果揭晓前封存的预测不能在事后修改，以保留真实预测和实际结果的差异。
- 持久对象的稳定 ID 独立于文件路径。
- 持久认知及配置属于沧海；恢复使用明确指定、解析为单个提交的完整状态，不依赖旧机器上的临时状态。

## 8. 评估边界

**实现正确性通过自动化验证；实际使用效果通过用户在真实使用中的反馈持续改进。**

自动化可以检查可观察、可复现的契约，例如资料是否留存、已知测试资料是否可召回、来源引用是否正确、修正是否传播、权限是否生效、预测是否保持原貌、恢复是否完整。

需要 LLM 判断的语义评测可用于发现问题和回归诊断，其评分不等于客观证明“已经理解用户”或“建议对用户有帮助”。现有合成用例、回归工具与工程门禁继续发挥验证作用，不能代替用户对实际效果的判断。

Stella 应从自然使用中的认可、拒绝原因、纠正、行动结果等反馈改进，不要求用户另行完成评分表或问卷。本轮没有确认以“有／无 Core 的 A/B 分数”作为实际体验通过门禁。

社交判断的回归诊断应覆盖：把礼貌或话题参与误当作关系投入、忽略投入不对等和状态变化、用人格标签掩盖反证，以及用后来结果污染历史判断。自动化可以核查来源、时间边界和反馈传播；语义诊断与后续结果帮助发现判断问题，不等于客观证明知晓对方内心或建议对用户有帮助。
